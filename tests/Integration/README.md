# Integration scripts

These scripts need a real environment (TwinCAT XAE/IDE open plus UmRT or a real runtime) and a solution containing the expected PLC variables. They are manual diagnostics, not automated unit tests. Pass `-SolutionPath` to point at your own solution.

| Script | Purpose |
|---|---|
| `bool-write.ps1` | Compare BOOL write methods (`WriteAny` vs raw 1-byte ADS write) and monitor the result |
| `write-verify.ps1` | Show that an ADS write sticks on a standalone variable but not on an FB VAR_INPUT that MAIN rewrites each scan |
| `list-symbols.ps1` | List MAIN-level symbols to find writable variables (`Get-TcSymbols`) |
| `full-cycle.ps1` | Full build -> activate -> login -> ADS -> run -> test cycle |
| `build-errors.ps1` | Inject an undefined identifier into a POU, `Build-TcProject` must return `BUILD_FAILED` with `buildSucceeded=false` and `codeErrors` (file/line from the XAE Error List via `Get-TcBuildErrors`), restore, build again (`buildSucceeded=true`, `codeErrors` empty). **It modifies the POU file on disk** (XAE saves before build): the switch `-IUnderstandThisModifiesTheProject` is mandatory (exit 2 without it), a solution under OneDrive is refused (exit 3), and the POU is copied to `<POU>.TcPOU.bak-<timestamp>` before the injection and restored from it by file copy in a `finally` block (the .bak is deleted once the restore verified). Run it only against a local COPY of a solution; run under an outer deadline (e.g. `Start-Process powershell.exe -PassThru` + 300 s) because a full compile can pop the XAE "Assertion Failed" box (if the deadline kills the script the .bak stays next to the POU for a manual restore), and pass `-CleanCompileInfo` to delete `plc\_CompileInfo` first |
| `login-flag-experiment.ps1` | Experiment: which `Login(nFlags)` value the runtime accepts (`-Flag`, optional `-SilentMode` / `-SuppressUI`). It Activates and downloads, so use only your own solution |
| `reload-experiment.ps1` | Experiment: does a running XAE pick up a `.TcPOU` changed on disk by another tool (`-Scenario S0a/S0b` baseline closed/open in editor, `S2a/S2b` VS auto-reload options, `S3` Solution close + reopen, `S3b` Project Unload/Reload); judges reload dialog (UIA), `Get-TcPouCode`, and `Build-TcProject` C0046. Modifies the POU on disk (`-IUnderstandThisModifiesTheProject`, OneDrive refused, `.bak` restored in `finally`), refuses to run while any TcXaeShell is running; log `logs/reload-<Scenario>.log` |
| `multi-ide.ps1` | Several IDEs on the desktop at once: starts a 32-bit XAE with ANOTHER solution (A), an empty 32-bit XAE (B) and, when installed, an empty VS2022 (C), then checks that `Connect-TcIde -SolutionPath <target> -ProgId` LAUNCHES a new instance (`selectedBy=launched`, `ideProcessId` not A/B/C, `candidates[]` lists A and B, A/B untouched), that a second call is `solution-match` on the same pid, that a modal dialog opened in A (`DTE.ExecuteCommand('Tools.Options')` from a background job) is invisible to `Get-TcIdeModalDialog` on the target but found with `-ProcessId <A>`, that `Build-TcProject` succeeds in the target, and that `Disconnect-TcIde -Quit` ends only the target pid. Every step is one JSON line in `-LogPath` (default `logs/multi-ide.log`); exit code = failed steps; `-DeadlineSec` (default 900) bounds the whole run and the pids it started go to `<log>.pids.json` for an outer watchdog. Refuses to run when the target solution is already open somewhere (that instance would be quit at the end); IDEs already running are never touched. No Activate, no runtime needed |
| `false-success.ps1` | #28 / #32 "no false success" scenarios against the local UmRT: removes the `Build.0` line of `FrameworkUnitTest` (port 852) from a COPY of a two-PLC solution and checks `Build-TcProject` (`PROJECT_SKIPPED_BY_CONFIGURATION` warning; failure with `-ExpectedProject`), restores it, runs the multi-PLC `Enable-TcConfig -Force` (851 + 852 Run, boot package SHA-256, final readback), nested / alias ADS reads on 852, `Set-TcSystemState` Run -> Run (`leftOriginal`) and a Run that a second process turns back to Config (`SYSTEM_STATE_MISMATCH`). One JSON line per step in `-LogPath`; `-DeadlineMin` (default 45) bounds the run; closes its IDE. Needs `-Sln <copy> -FwGuid <FrameworkUnitTest project GUID>` |
| `Watch-Runtime.ps1` | Background watcher to run during every real-machine test (`docs/agent-brief-realmachine.md`): every `-IntervalMs` (default 1000) one JSON line in `-LogPath` (default `logs/runtime-watch.jsonl`) with time, `TcSystemServiceUm` pid set (`pid` = lowest or null, `pids` sorted), port 10000 AdsState of `-AmsNetId` (default `199.5.42.250.1.1`, the local UmRT_Default of the test PC only; `unreachable` + `adsError` when the read fails) and the size of `UmRT_Default\3.1\Boot\TCNC.bootdata`; an extra `event` line when the sorted pid set changes or the bootdata becomes 0 bytes. `-DurationSec 0` (default) runs until stopped; in tests pass the overall deadline and `Start-Process -PassThru`, then stop only that pid. Read-only, never throws for a missing runtime |

## Projects with missing libraries (#45 / #56)

On a solution whose Error List shows unresolved libraries (Library Manager rows, e.g. the TwinCAT_Festo copy) `Build-TcProject` stops at `LIBRARY_UNRESOLVED`, and since #56 that result is also recorded as BUILD_REQUIRED, so a following `Enable-TcConfig` / `Enter-TcPlcOnline` refuses. `bool-write.ps1`, `build-errors.ps1`, `false-success.ps1`, `login-flag-experiment.ps1`, `reload-experiment.ps1` and `write-verify.ps1` take `-AllowUnresolvedLibrary` and pass it to `Build-TcProject` (since #61 such a build is never complete - `completeBuild = false` - so a following `Enable-TcConfig` / login still returns BUILD_REQUIRED; to Activate, install the libraries first).

**`build-errors.ps1` is weak on such a project**: step 4 accepts `LIBRARY_UNRESOLVED` instead of `BUILD_FAILED`, and step 4b does not require the injected C0046, because with missing libraries XAE may not compile the PLC code at all (measured 2026-10-25, TcXaeShell 4024, TwinCAT_Festo copy with 7 unresolved libraries: no C0046, LastBuildInfo 0). The script then does not prove that code errors are reported. To verify the code-error path, run it against a solution WITHOUT missing libraries. `reload-experiment.ps1` (its C0046 check, 3.) has the same limit.

Unit (no IDE / runtime): `tests/Unit/*.ps1`, run by `scripts/check.ps1` (check `unit`, also in CI; skipped with `-Fast`). `tests/Unit/activate-timeout.ps1` exercises the `ActivateConfiguration()` deadline (`ACTIVATE_TIMEOUT` at the deadline with diagnostics, in-time return, error rethrow, `IDE_CRASHED`) with a mocked background call; exit code = failed checks.
